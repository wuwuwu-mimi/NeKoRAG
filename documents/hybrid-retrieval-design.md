# RAG 混合检索：当语义不够，让关键词来救场

> 一个自建 RAG 系统的检索架构复盘：为什么需要双路召回 + RRF 融合

---

## 问题：纯向量检索的盲区

我在 NeKoRAG 项目里最初只用了 **稠密向量检索（Dense Retrieval）**：

```
query → bge-m3 embedding → ChromaDB cosine 相似度 → top_k 切片
```

这套方案在大多数情况下表现不错，但很快遇到了几个典型的失败场景：

### 场景一：专有名词漂移

查询「**HD36 泡沫**的技术参数」，向量模型可能把"泡沫"的语义拉到「海绵」「发泡材料」「缓冲材料」上，漏掉了含精确字符串 `HD36` 和 `泡沫` 同框出现的切片。

### 场景二：编号 / 缩写匹配

查询「**SW-50 椅子**的最大承重是多少」——`SW-50` 是产品编号，向量模型对此没有任何语义理解，只能靠字面碰运气。

### 场景三：低频术语

某篇文档提到了 `改性尼龙`，这个词在整个知识库只出现两次。向量模型对低频词的 embedding 天然不敏感，召回率极低。

这些场景的共同特点：**需要的是精确的字面匹配，而非语义近似。**

---

## 解法：双路召回

借用信息检索领域几十年的经验，在稠密检索之外并行接入 **稀疏检索（Sparse Retrieval）**。

| | 稠密检索（Dense） | 稀疏检索（Sparse） |
|---|---|---|
| 算法 | Embedding + 余弦相似度 | BM25（TF-IDF 的现代版本） |
| 擅长 | 语义相似、同义词、改写表述 | 关键词精准命中、专有名词、编号 |
| 盲区 | 低频术语、精确字符串匹配 | 同义词、跨语言、长文本语义 |
| 实现 | ChromaDB + bge-m3 | rank_bm25 + jieba |

两者的能力天然互补——稠密检索覆盖「意思相近」，稀疏检索覆盖「字面一致」。

### BM25 为什么不是 TF-IDF

BM25 在 TF-IDF 的基础上做了两个关键的修正：

1. **词频饱和**：同一个词出现 100 次和出现 10 次，TF-IDF 会给 10 倍的权重差，但这对检索来说过度了。BM25 用非线性函数让词频权重趋于饱和——出现 3 次就说明很相关了，出现 30 次不会更相关 10 倍。
2. **文档长度归一化**：长文档天然包含更多词，TF-IDF 直接惩罚长文档。BM25 用一个可调参数控制长度惩罚的力度，避免短文档获得不公平的优势。

### 中文分词：为什么不能省

英文 BM25 可以直接按空格切词。中文没有天然分隔符，必须用分词器。我选了 **jieba 精确模式**，并过滤掉单字符 token（`的`、`是`、`了` 等），这些词在所有文档中高频出现且不携带语义信息，对 BM25 的 IDF 计算反而有害。

```python
# 分词 + 去噪
tokenized = [
    token for token in jieba.lcut(text)
    if len(token.strip()) > 1
]
```

## 融合：RRF（Reciprocal Rank Fusion）

两路检索各返回一个排序列表，如何合并成最终结果？

直觉做法是把两边分数归一化后加权求和。但这有两个问题：
- 向量相似度（0~1）和 BM25 分数（0~∞）的量纲完全不同，归一化依赖于对分数分布的假设
- 调权重（向量 0.7 + BM25 0.3？）需要大量标注数据做网格搜索

**RRF 避开了这些坑**——它只看排名，不看原始分数：

```
RRF(chunk) = Σ 1 / (k + rank_i)
```

- `rank_i`：该 chunk 在第 i 路检索器中的排名（从 1 开始）
- `k`：平滑常数，通常取 60

如果一个 chunk 在 Chroma 排名第 1、在 BM25 排名第 5，它的 RRF 分数就是 `1/(60+1) + 1/(60+5) = 0.0164 + 0.0154 = 0.0318`。

**为什么 k=60？** 如果 k=0，排名第 1 的分数是 1，排名第 2 是 0.5——差距过大，几乎等于只看各路的第 1 名。k 越大，排名靠后的结果也能获得可观的分数，融合更平滑。60 是大量实验收敛的经验值。

### RRF 的优势

- **不需要调权重**：没有超参数需要搜索
- **对分数分布鲁棒**：不管原始分数是余弦相似度还是 BM25 分数，排名总是一致的
- **容易扩展第三路**：加一路新的检索器（比如基于实体的召回），就是多一个 `1/(k + rank)` 的加项

## 架构总览

```
                      query
                        │
           ┌────────────┴────────────┐
           │                         │
     bge-m3 embedding          jieba 分词
           │                         │
     ChromaDB.query            BM25Okapi.get_scores
           │                         │
     [(id, rank), ...]        [(id, rank), ...]
           │                         │
           └────────────┬────────────┘
                        │
                  RRF 分数融合
                        │
                  最终 top_k ID
                        │
                  (可选: reranker)
                        │
                   返回结果
```

入库管线也从三步扩展为四步：

```
加载文档 → 双层切片 → ChromaDB 向量入库 → BM25 索引构建 & 持久化
```

BM25 索引（分词语料 + 切片数据）用 pickle 序列化到 `data/bm25_index/`，服务启动时加载，避免每次重启都要重新分词。

## 局限与后续方向

1. **jieba 分词对未登录词不友好**：产品编号（`SW-50`）、技术缩写（`HD36`）可能被错误切分。解法：维护自定义词典 `jieba.load_userdict()`。
2. **BM25 索引全内存**：语料量级大（>10 万切片）时内存和构建时间会成问题，届时可迁移到 Elasticsearch 或 Meilisearch 做 BM25 后端。
3. **缺少 reranker**：融合后仍用 RRF 排序，没有 cross-encoder 做精排。下一步在 `reranker.py` 引入 bge-reranker 做最终排序。
